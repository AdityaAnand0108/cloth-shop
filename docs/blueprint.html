01 — Ground rulesScope & assumptions

Everything below is designed for one physical shop in India with a handful of staff, billing at a counter. There is no barcode scanner — each type of cloth carries a short code that the cashier types. The schema is multi-store-ready — every stock and sales row carries a store_id — but nothing else is built for scale you don't have.

Assumptions this design rests on
AssumptionConsequence if wrong
India / GSTTax module changes shape: HSN, CGST-SGST split and place-of-supply logic all become dead weight.
1 store, 2–6 usersNone near-term. Multi-store needs stock transfers and per-store number series — both already in the schema.
Counter POS first, no web storefrontAn online store adds a reservation model on stock and an order-fulfilment state machine. Plan it as Phase 5, not a retrofit.
No scanner — a typed code per cloth typeItem lookup becomes a search problem instead of an exact-match problem. The POS entry box turns into the highest-risk piece of UI in the system. See Item codes & entry.
The code identifies the style, not the sizeIf your codes already go down to size and colour, the variant picker becomes optional and billing gets one step shorter. The design supports both.
Some goods sold by the metre (fabric, not garments)Quantities must be decimal from day one. Retrofitting NUMERIC(12,3) over integer stock is painful.
One decision to make now

Do you sell cut fabric by the metre as well as stitched garments? It changes the unit-of-measure handling, the label format and the return rules. The design below assumes yes, because supporting both is much cheaper than adding it later.

02 — ShapeArchitecture

Build a modular monolith: one Spring Boot application, one database, strict package boundaries between modules. Not microservices. A shop doing a few hundred bills a day gets nothing from a service mesh except a distributed-transaction problem you'd have to solve to keep stock and billing consistent.

The discipline that matters is internal: each module owns its tables, exposes a Java interface, and never reaches into another module's repositories. If you ever do need to split something out, the seams are already cut.

The client-side catalog is now load-bearing

With a scanner you look up one exact barcode and a server round trip is fine. With a typed code you are searching — on every keystroke, while a customer waits. So push the entire catalog to the browser: a shop with 20,000 variants is a few megabytes of JSON, which IndexedDB holds comfortably. Search runs locally against an in-memory index, which means sub-millisecond results, no spinner, and no dependence on your broadband.

Sync it as a delta: GET /catalog/sync?since= returns rows changed since the client's watermark. Poll every few minutes and on window focus.

Why the offline outbox is not optional

Your broadband will go down, and it will go down on a Saturday evening. If billing stops, the shop stops. Queue completed bills in IndexedDB with a client-generated idempotency_key, print from local data, and sync when the connection returns. The server treats a replayed key as a no-op and returns the original bill.

The one thing that can't work offline is a live stock check across terminals — accept that. With one counter it doesn't matter; with three it means an oversell you reconcile at day close.

05 — Core modelThe variant model

This is the decision that separates a clothing system from a generic inventory system, and getting it wrong is the most expensive mistake available to you. A "shirt" is not a thing you stock. A blue Oxford shirt in size M is a thing you stock — it has its own count and its own price, and it can sell out while the same shirt in L sits on the shelf.

So: product holds what is shared (name, category, HSN, tax rate, item code, images). product_variant holds what varies (size, colour, cost, price, stock). Stock never hangs off product.

Your codes sit at the product level: one code for "cotton Oxford shirt", not nine. That keeps the code short enough to type and short enough to read off a tag — and it makes the size-and-colour choice an explicit step at the counter, which is where a person is looking at the garment anyway.

Don't build an EAV attribute system

You will be tempted to build generic attribute / attribute_value tables so you can add "sleeve length" later without a migration. For a shop selling clothes, plain size and colour columns on the variant are the right call: every query stays readable, indexes work, and the size-curve report is a GROUP BY instead of three joins. Add a JSONB attrs column for the rare extra. Revisit EAV only if you start selling something genuinely different.

06 — CounterItem codes & entry

With no scanner, the item code is the interface. Your staff will type it a few hundred times a day, read it off a tag in bad light, and shout it across the shop. Design it for that, not for a database.

The code scheme

Use a letter prefix plus a numeric serial: SH104, SR038, FB211. The prefix comes from the category and the serial is auto-issued per prefix, so codes stay short, sort sensibly, and tell a human what they're looking at before the screen does.

Prefix scheme — adapt to what you actually stock
PrefixCategoryExample
SHShirtsSH104 — cotton Oxford, full sleeve
TST-shirtsTS027 — round neck, printed
TRTrousersTR058 — formal, poly-viscose
KUKurtisKU312 — rayon, A-line
SRSareesSR038 — Kanjivaram silk
DMDress materialDM145 — unstitched 3-piece
FBFabric by the metreFB211 — suiting, 58" width

Five rules for the scheme

  1. Four to six characters, hard limit. Every extra character is a typo per hundred bills. If the code needs a seventh character your prefixes are too granular.
  2. Letters only in the prefix, digits only in the serial. This is what kills the classic ambiguities — nobody wonders whether SH104 has a letter O or a zero, because the digit half can't contain letters.
  3. Normalise on lookup. Uppercase, strip spaces and hyphens, then match. Store the normalised form in code_norm and index that, not the display form.
  4. Codes are immutable and never reused. Once a code is printed on a tag it is out of your control. Retiring SH104 and reissuing it next season is how last year's price ends up on this year's shirt.
  5. Auto-issue, never hand-type. The serial comes from number_series keyed by prefix. Letting staff invent codes guarantees duplicates and gaps.

What happens when the cashier types

Accuracy is the cost you're paying

Be clear-eyed about the trade. A scan is roughly one second and cannot select the wrong item. Typing a code is three to five seconds and introduces an error class that scanning simply doesn't have: the cashier bills SH104 when the tag said SH140, the customer pays a plausible-looking price, and your stock is now wrong on two products at once. Nobody notices for weeks.

Three compensating controls, all cheap:

  • Mandatory visual confirmation. The line does not commit until the product name, colour, size and price are on screen at a size readable from standing. This alone catches most transpositions, because SH140 renders as "Silk Saree" and the cashier is holding a shirt.
  • Stock-aware picker. Out-of-stock cells are visible but unselectable. Billing a variant you have zero of is usually a sign you typed the wrong code.
  • Weekly cycle counts, from Phase 2. Count one category a week rather than waiting for an annual stock take. With scanning you can defer this; without it, you can't.
Design the input so a scanner would just work

Keep a nullable barcode column on the variant and treat the entry box as "accepts a code, however it arrives" rather than "a text field a person types into". A USB barcode scanner is a keyboard-wedge device — it types the code and presses Enter, no drivers and no integration. If you ever decide the accuracy is worth ₹1,200 of hardware, it drops into this design with no schema change and no new screen. Costs you nothing to leave the door open.

07 — Core modelStock as a ledger

The second modelling decision. Never store stock as a number you update. Store it as an append-only ledger of movements, and keep the current quantity as a derived cache.

The reason is practical, not academic. Sooner or later a count will be wrong, and the only question that matters is "how did it get to 37?" A ledger answers it in one query. A mutable integer answers nothing.

In code this is one InventoryService.post(movement) method that inserts the ledger row and upserts the cache. Make it the only way stock changes anywhere in the codebase, and unit-test that invariant.

09 — Critical pathCheckout flow

This is the transaction you must get right. Everything else in the system can be slow or slightly wrong and the shop still runs; if billing double-charges or loses stock, it doesn't.

Sequence, in words

  1. Cashier types a code; the client resolves it against the cached catalog and shows the item for visual confirmation before the line commits.
  2. Client posts the cart with a UUID it generated when the cart was created.
  3. Server rejects a replayed key by returning the existing invoice — same response, no second bill.
  4. Server recomputes every price, discount and tax. Client-sent totals are used only to detect a mismatch and log it.
  5. Invoice number is drawn from number_series under a row lock, scoped to store and financial year.
  6. Invoice, items, payments, stock ledger rows, on-hand cache and loyalty points all commit together or not at all.
  7. Print and messaging fire after commit, through an outbox so a provider outage retries instead of failing the sale.

10 — PricingDiscount engine

You asked for discounts specifically, so here is the shape rather than a hardcoded percentage field. Model a discount as a rule with conditions, evaluated by an engine that takes a cart and returns priced lines. The POS calls the same engine for its live preview that the server calls at checkout — one implementation, exposed over an endpoint, so the two can never disagree.

Rule types to support
TypeExampleApplies at
PERCENT20% off all Kurtisline
FLAT₹200 off this itemline
BILL_PERCENT10% off the whole billbill
THRESHOLDSpend ₹5,000, get ₹500 offbill
BUY_X_GET_YBuy 2 shirts, third free (cheapest free)line group
TIERGold members always get 5%bill
COUPONCode DIWALI25, 500 uses, once per customerbill
MANUALCashier negotiates ₹150 off — needs approval and gets loggedline or bill

Evaluation order

  1. Match every active rule whose date window and conditions fit the cart.
  2. Sort by priority. Apply line-scoped rules first, then bill-scoped.
  3. A non-stackable rule that fires excludes lower-priority rules on the same line. Where two could apply, pick the one better for the customer and record which lost.
  4. Clamp each rule at its max_discount_amount, then clamp the bill at a global maximum-discount policy.
  5. Write one applied_discount row per rule that fired.
Two things that bite people

Discount before tax. Under GST the taxable value is the price after discount. Computing tax on MRP and then subtracting the discount overstates your output tax and is wrong on the invoice.

Rounding. Distribute a bill-level discount back across lines proportionally, then fix the last line so the parts sum exactly to the whole. Otherwise your line totals won't add up to the bill total and your accountant will ask why.

The report that pays for this module

Discount given vs. margin, sliced by staff member. It's how you find out that one cashier is quietly giving 15% to everybody, and whether your Diwali offer actually sold anything or just handed money to people who would have bought anyway.

11 — Non-negotiableEngineering rules

Short list, all learned the expensive way. Put it in your CLAUDE.md or contributing guide.

Money & numbers

  • Money is NUMERIC(12,2) and BigDecimal. Never double, never float. One rupee lost per bill is thousands a year.
  • Quantity is NUMERIC(12,3) so 2.5 metres works.
  • Percentages are NUMERIC(5,2), stored as 5.00 not 0.05. Pick one and never mix.
  • Always pass an explicit RoundingMode.HALF_UP.

Documents

  • invoice_item snapshots name, SKU, HSN, price and tax rate. A bill from last year must reprint identically after you rename the product.
  • Store cost_at_sale on the line, or your margin reports rewrite history every time cost changes.
  • Financial records are never deleted. Void writes a reversing document; hard DELETE is not available to the application.
  • Invoice numbers are gapless per financial year, allocated under a row lock.

Concurrency & safety

  • Item codes are normalised (uppercase, strip spaces and hyphens) on write and read. Uniqueness is enforced on code_norm, never on the display form.
  • A code, once issued, is never edited and never reused — including after a product is discontinued.
  • Every mutating POST accepts an Idempotency-Key. Checkout, GRN posting and payment recording require one.
  • @Version on inventory_stock; retry the transaction on an optimistic-lock failure.
  • Stock changes only through InventoryService.post(). Enforce with an ArchUnit test.
  • Never trust a client-computed total. Recompute, compare, log the delta.

Operations

  • Timestamps stored UTC as timestamptz, displayed in IST.
  • Flyway migrations from commit one. No ddl-auto: update in any environment.
  • Audit log on price changes, voids, discount overrides, stock adjustments and cost views.
  • Nightly encrypted pg_dump offsite, and a restore actually rehearsed once a month. An untested backup is not a backup.
Verify before you code the tax module

Indian textile and apparel GST slabs have been revised more than once, and rates can depend on the item's price. Keep every rate in tax_rate with an effective_from date, resolve by HSN and invoice date, and confirm the current values with your CA rather than trusting any number in this document or in a tutorial.

  • React 18 + TypeScript, built with Vite.
  • TanStack Query for server state; Zustand for the cart only. You do not need Redux here.
  • Tailwind + shadcn/ui for the back office; a hand-built, deliberately plain POS screen with large type and a permanently focused entry box.
  • React Hook Form + Zod, sharing the validation shapes with the API contract.
  • Dexie over IndexedDB for the cached catalog and the bill outbox.
  • MiniSearch (or a hand-rolled prefix map) for in-browser code and name lookup. A few thousand variants index in milliseconds; do not send keystrokes to the server.
  • Print via a hidden iframe with @page CSS for A4, and the local agent for 80 mm thermal.

Back end

  • Spring Boot 3.x on Java 21 — records, pattern matching, virtual threads.
  • Spring Web, Data JPA, Security, Validation, Actuator.
  • Flyway for migrations, MapStruct for DTOs, Testcontainers for tests against real Postgres.
  • jasperreports or plain HTML→PDF for the A4 tax invoice.
  • OpenAPI via springdoc; generate the TypeScript client from it.
  • Skip Redis, Kafka and Elasticsearch until something actually hurts.

Where it runs

One small VPS — 2 vCPU, 4 GB — running Docker Compose with three containers: Postgres, the Spring Boot jar, and Nginx serving the React build and terminating TLS. That is roughly ₹600–1,200 a month and will comfortably serve a shop doing a few hundred bills a day. Kubernetes would be a hobby, not an improvement.

The part people skip

Nightly pg_dump, encrypted, pushed offsite, with a retention window. Then restore it into a scratch container once a month and open the app against it. The shop's entire transaction history and your GST filings live in that one database. Losing it is the only failure in this document you cannot recover from.

14 — SequenceBuild order

These phases are genuinely sequential — each one is usable on its own, and each depends on the one before it. Ship Phase 1 into the actual shop before writing a line of Phase 2. Real bills will teach you more about what to build than any plan, including this one.

01
Bill something

Auth and roles, category / brand / product / variant, the item-code scheme and tag printing, opening stock entry, the stock ledger, the cached-catalog code search and variant picker, POS billing with split payment, GST calculation, thermal receipt. The shop can open on this alone.

wk 1–6
02
Close the loop

Purchase orders and GRN, supplier ledger, returns and exchanges with credit notes, hold/recall, customer records, expenses, register day close, quick-pick tiles, weekly cycle counts, and the first four reports.

Sell smarter

The discount rule engine and coupons, loyalty points and tiers, store credit, WhatsApp bills, alteration jobs, dead-stock and size-curve reports, offline billing, GSTR-1 extract.

Scale the operation

Second location and stock transfers, physical stock take, gift cards, salesperson commission, per-store number series, an owner dashboard that works on a phone.

05
Go online — only if you want to

Customer-facing catalog, stock reservation, order fulfilment states, payment gateway, delivery partner. This is a second product sharing a database, not a feature. Decide deliberately.

later

What to cut if you're short on time

Gift cards, commission, the online store, and anything in Phase 4 or 5. What you cannot cut: the variant model, the item-code scheme, the stock ledger, gapless invoice numbering, snapshot pricing on invoice lines, and backups. Those are structural — retrofitting any of them means migrating live financial data, or reprinting every tag in the shop.
